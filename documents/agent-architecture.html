Agent architecture: current → future

How a household query is routed today through a ReAct loop — reason, call a tool, observe what it returns, repeat until there's enough to answer — and how that same loop nests one level deeper once Homly has more domains than one tool list should hold.

  • Both entry points — /query and /internal/graph-invoke — resolve to the same loop through one compat shim.
  • One flat registry, agents/orchestrator/registry.py — four domain agents (expenses, insurance, pantry, savings), one tool list the LLM sees every round.
  • agent_node and tools_node cycle — Claude can chain a lookup in one domain off what it learned in another, not just pick tools once and stop.
  • The final answer is Claude's own text once it stops calling tools — no separate synthesis call, no canned fallback for off-topic messages.
  • household_id is threaded through SupervisorState, never re-derived inside an agent.
  • The LLM call goes through OpenRouter, not Anthropic directly — one API key for every model in the app, Claude included.

  • Same entry point, same LLM adapter — only the middle of the stack grows.
  • registry.py becomes a registry of team supervisors, not agents directly. Each team keeps today's flat registry underneath it.
  • Adding a new app means writing one team supervisor plus its agents and registering it once at the top — the top-level tool list stays small no matter how many teams exist.
  • A compound question ("spending and insurance renewals") is answered the same way Fig. 1 already answers one — the top supervisor's loop calls both teams (in parallel within a round, since neither depends on the other) and keeps going until it has both pieces.

What actually changes

Fig. 2 is not a rewrite of Fig. 1 — it's the same loop nested one level deeper. agent_node and tools_node already reason across domains in a single pass today; a team supervisor is the identical cycle, just bound to a narrower registry. From the top level's perspective, an entire team is indistinguishable from any other tool — it takes a query, reasons and calls its own agents internally, and hands back an answer.

The only genuinely new code per domain is one more team-supervisor module reusing that same loop — agent_node bound to a team's own tools, cycling through tools_node until it has enough to answer — not a new pattern to design, the one agents/orchestrator/supervisor.py already runs today.
